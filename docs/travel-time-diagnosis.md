# v0.2.1 移動時間マスタの調査・改修記録

## 確認できた旧実装の状態

- 管理画面と旅行者画面の保存キーは両方 `booktrip-travel-times-v1`。キー違いは確認されなかった。
- JSONはTravelTime配列。作品ID、方向付きのスポットID/自由入力名、交通手段、分数、確認日、確認状態を持つ。
- 管理画面の初期作品が `books[0].id` 固定で、旅行者の選択bookIdを受け取っていなかった。
- 新規管理区間の交通手段が `transit` 固定だった。旅程がwalkingやdrivingの場合はその時間を使えない。
- 検索に作品IDの条件がなく、管理画面の表示対象と旅程照合の条件が揃っていなかった。
- verified、確認日、整数の所要時間が必要だったが、未反映の理由を表示していなかった。手動値の優先が見えにくかった。
- v0.2.0には管理画面から戻る際の再読込と既存旅程のstate更新は存在した。正常な同一作品・交通手段・確認済みデータの反映はクラウドで再現でき、全件の保存・更新が壊れているとは確認していない。
- 単体HTMLは同一ファイルのハッシュで切り替え、画面遷移でリロードしない構成。ファイル位置やブラウザを変えた場合の保存領域はブラウザ仕様に依存する。利用者のWindows上の実データと保存ポリシーはこの環境からは確認できない。
- 初期マスタは作品内のスポット間だけで、自由入力の出発地→最初のスポットと最後のスポット→帰着地は含まない。途中の区間だけを登録しても、未入力の往路があればその地点以降の予定時刻は未確定になる。帰着予定には復路の時間も必要。これを旅程サマリーにも明記する。
- 初期JSONの9区間は意図的にunverified、時間と確認日はnull。未検証データを確認済みへ変更してはいけない。

## 改修

Appで旅行者の選択bookId/交通手段を保持し、管理画面の初期値へ一方向に渡す。管理画面内の選択変更は旅行者へ返さない。

保存、検証、読込、照合は `src/lib/master.ts` に集約。保存前の検証・書込み後の読み戻し・成功通知を行う。JSON出力はlocalStorageを更新しない。

各区間にbookIdを付与し、作品・端点・方向・交通手段が合う登録だけを検索。手動値は保持し、マスタ由来の値は再評価する。不適合・不足条件は理由付きで表示し、保存データの読込失敗も通知する。確認状態を自動でverifiedへ変更しない。

## 保存形式の例

```json
[
  {
    "id": "example",
    "bookId": "botchan",
    "fromSpotId": "dogo-onsen",
    "toSpotId": "dogo-park",
    "travelMode": "transit",
    "durationMinutes": null,
    "checkedAt": null,
    "sourceUrl": null,
    "verificationStatus": "unverified"
  }
]
```

これは形式例で、確認済み時間の例ではない。空のスポットIDを使う場合はfromPlaceName/toPlaceNameに自由入力地点名を保存する。施設名から作品名への推測や逆方向の流用はしない。旧レコードの作品ID省略はスポットIDから一意に分かる場合のみ互換対応する。

## 検証範囲

単体テストでは保存→読込→既存旅程への適用と時刻再計算、キーとJSON形式、保存失敗時の非通知、未確認の維持、作品/地点/方向/交通手段/確認日/時間の判定、重複・旧形式を検証する。

ブラウザではWeb版と単体HTML版をHTTP配信して実際に操作する。古都の引き継ぎ、管理側の作品変更からの保護、坊っちゃんの保存と反映、手動値の保持、不一致理由、JSON出力との分離、書込み拒否、日付と時刻の別コピーを確認する。

新版Windows ARM64のEdge実機、file://表示、Google Maps実画面の日時UI/貼り付け可否は未確認。クラウドのfile://ポリシーは回避しない。
